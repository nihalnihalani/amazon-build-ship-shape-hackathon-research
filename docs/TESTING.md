**Read the evidence class before quoting a result.** Everything here is `automated` or `web_preview`. **No suite uses a real phone microphone, the Vega runtime, a Vega Virtual Device, a physical Fire TV or AWS**, and no result may be promoted to those classes:

| Class | Meaning in this repository |
|---|---|
| `automated` | A command run on this host with an exit code and counts. Uses fakes, mocks, synthetic audio (sine waves) or a headless TV core. |
| `fixture_replay` | Numeric or synthetic-audio replay through real code paths (the phone test build). Labelled "Fixture replay" in the product. |
| `web_preview` | The TV UI rendered by react-native-web in desktop Chrome with shims. **Not Vega**: no VoiceView, no Vega focus engine, no real UI-scale setting. |
| `documentation_only` | Read from a page, registry or repository; not exercised. |
| `real_phone`, `real_VVD`, `physical_Fire_TV` | **No result of these classes exists.** |

Pass counts prove the tested arithmetic, state machines and wiring. They do not prove microphone validity, Vega compatibility, privacy of a deployed service or store acceptance.

**`production.mjs`: failed at `63af0ae`, reworked and passing at `ac556df`.** The first version assumed that in headless Chrome 154 a real, unanswered `getUserMedia` call stays pending. In the clean-clone run (twice) the same headless Chrome rejected the call immediately with `NotAllowedError` (a probe on a blank page returned `REJECTED:NotAllowedError` at once), so the script failed three checks in its part A and never reached its stubbed-audio part B. EV-0019 had recorded a pass earlier in the day, so the behaviour changed on this host; a probable cause is the operating-system microphone permission state of Google Chrome (unverified: no privileged check was made and no system setting was changed). The phone owner reworked the script (merged as `734c20b`): it accepts **both** legitimate outcomes, checks each against its own UI (pending: "Waiting for permission" and a working Cancel; immediate denial: "Permission denied", re-enable guidance and Start offered again), and prints which one happened. Observed at `ac556df` on this host: `npm run e2e:production -w @atr/phone` exit 0 twice, 31 checks each, outcome `immediate_not_allowed` after about 72 ms (71 and 74 ms), including the formerly unreachable part B. `ATR_E2E_SIMULATE=pending` holds the real request unanswered to exercise the pending branch on a host that denies at once: exit 0, 30 checks, labelled **SIMULATED** in its output. So the pending branch is evidenced only as a simulation on this host; the real-microphone behaviour of a physical phone is still not tested (B-002).
