# Relay security notes

Scope: `services/relay` (core, local server, Lambda adapters) and `infra/`. Specs: ADR-0002 (privacy and logging), ADR-0003 (pairing and authentication), ADR-0006 (transport), `docs/adr/AMENDMENTS-REV2.md` (the rows owned by the relay), PROTOCOL.md revision 4. This is the implementer's account for the independent security review; it is not a review. The threat-model checklist ids (SEC-*) are in `docs/security/THREAT_MODEL.md`; the tests carry them in their names.

Evidence class of everything here: **automated** (unit and local integration tests, including the same scenarios run against the in-memory store and the strict DynamoDB model) and **documentation_only**. Nothing was exercised against AWS.

## 1. What the relay validates on every message

One entry point does all of it: `RelayCore.processInbound(frame, ctx)`. The local server and the Lambda adapter hand it the frame as it arrived (a string for a text frame, a size-only marker for any other frame, never decoded) and nothing else; a test fails if either adapter calls anything else with network data or parses it itself. The validator is `@atr/protocol`, reached through `src/core/protocol-port.ts`.

Order, with the one deliberate deviation from PROTOCOL.md section 4 called out:

1. Frame: text only (binary: `binary_rejected`, close 1003; on the Lambda adapter a base64 body is measured from its length and never decoded), at most 8192 UTF-8 bytes (`payload_too_large`, close 1009), checked before any parse.
2. JSON object with exactly the twelve envelope fields and `protocol_version` 1; unknown type; audio guard (keys `audio`, `pcm`, `samples`, `waveform`, `blob`, `buffer`, `data` at any depth, strings over 256 code points, arrays over 16, binary values: `audio_rejected`); envelope formats, identity binding and room rule; exact payload schema with ranges, enums, quantisation and text rules (`bad_schema`). The result is the validated clean copy.
3. Authentication phase: before authentication only `room.create`, `join.request`, `auth.resume` and `ping` are processed; at most 5 messages and 5 s (65 s while a join is pending), enforced on every message and by the deadline check (sweep locally, SQS on AWS, section 5).
4. Per message once authenticated, from stored state and not from connection memory: room exists, is not closed and not past its 12 h life; the role credential exists (not revoked) and is not expired; the connection's **role epoch** equals the room's current epoch for that role (`unpair`, `room.close`, reuse revocation and every new phone claim bump it, so at most one in-flight message can pass after a revocation; a resume changes the generation instead, which supersedes the older connection); the connection's generation equals the slot's (else `superseded` and close); `sender_role` equals the authenticated role; the type may be sent by that role (`forbidden_direction`); the envelope `room_id` equals the connection's room.
5. Rate limits (phone 40 per second sustained, burst 60; TV 20 and 40). **Deviation:** PROTOCOL.md puts rate limiting at step 9, after the duplicate, generation and sequence checks. The relay limits first, before step 8, so a flood of duplicates or replays costs a counter write and not a conditional write each, and a rate-limited message never records its id (SEC-A13: a rate-limited message does not burn its id). Observable behaviour is the same except for which error a message that is both rate-limited and stale receives.
6. Session binding (`stale` for a session id other than the room's active one), peer presence (`not_found`; `level` frames are dropped silently).
7. Duplicate `message_id` for this (room, role): dropped silently with the `duplicate_dropped` metric, before generation and sequence. The id is recorded atomically first and forgotten again if a later step rejects the message, so only accepted messages keep an id and a rejected one can be retransmitted. The local store keeps the last 1024 ids per (room, role); DynamoDB keeps ids for 60 s (a count window needs a hot item), the sequence check remains the hard guarantee.
8. `producer_generation` equals the current one (`stale`); strictly increasing sequence by conditional write (`replay`); per-session cue cap (`cue_limit`, three per room and session id announced in `session.begin`; no announced session means no cues).
9. Forwarding: the peer receives `JSON.stringify` of the validated clean copy (canonical form), never the received bytes, so duplicate keys, odd whitespace and escape variants collapse and nothing the validator did not see can pass through.

Credentials and codes: 32 random bytes (43 base64url characters) from `node:crypto`; stored only as domain-separated SHA-256 digests; compared with `timingSafeEqual` on equal-length digests. Pairing codes: six characters of the 22-character alphabet by rejection sampling (no modulo bias; tested exhaustively and statistically), stored as **HMAC-SHA-256 under a secret** because the code space is only about 26.8 bits (a plain hash of 26.8 bits is reversible by enumeration). The secret is random per process locally and an SSM SecureString on AWS, never an environment value (RUNBOOK.md section 6). Confirm digits: two digits by rejection sampling, with two decoys shown by the TV (number matching).

## 2. Credentials: rotation, the one-step grace, reuse, revocation

**Lifetime and rotation (A3-07, A3-11).** The credential issued at pairing (`room.created`, `join.accepted`) lives 2 hours, never beyond the room's own 12 hour life. Every successful `auth.resume` consumes the presented credential and answers `auth.ok` with a `next_credential` (also 2 hours), bumps the generation and leaves a tombstone of the consumed credential (a SHA-256 digest with its owner, kept until the consumed credential would have expired, at most 2 hours, after which it is simply unknown), all in one atomic step. Clients must store `next_credential` and use it for the next resume. The next credential is not stored in clear and is not random per call: it is derived as an HMAC of the room, the role and the digest of the consumed credential under the master secret (`HashKeys.nextCredential`), so the relay can compute the same value again without having kept it.

**Reuse revokes (SEC-A09).** Presenting a consumed credential anywhere outside the grace below is treated as a stolen or replayed credential: the relay increments the role epoch and revokes the role. A phone credential: the phone slot is revoked, a live phone connection gets `error revoked` and close 4410, the TV gets `error revoked` and `peer.state` (phone, disconnected), and the phone must pair again. A TV credential: the room is closed for both sides (`error revoked`, close 4411). The connection that presented the credential receives only the generic `unauthorized` (section 4). The `credential_reuse` event and metric count it (alarm `credential-reuse`).

**The one-step grace for a lost `auth.ok` (decision of 2026-10-05).** If the reply carrying `next_credential` is lost (a dropped socket right after the relay committed the rotation), the client still holds the credential that was consumed and would otherwise revoke its own role by retrying. The relay therefore accepts the credential consumed by the **last** rotation exactly once more, and only if all of these hold:

1. it is within 60 seconds of that rotation (`CREDENTIAL_GRACE_MS`);
2. the credential issued by that rotation has **not been presented yet** (the slot still holds it);
3. the grace has not been used before for this rotation;
4. the presented credential is the one consumed by the most recent rotation, and no other (a credential consumed two rotations ago is plain reuse).

When it applies the relay re-issues the **same** next credential (re-derived, as above) and does not rotate again (the stored credential stays N); the new connection is attached like any resume (generation bump, the old connection superseded, the TV told), and the grace is spent. Everything else is reuse and revokes: a retry after the next credential has been used, a retry after 60 seconds, a second retry. Tests (`test/core.credentials.test.ts`, both stores): lost `auth.ok` then a retry inside 60 s succeeds with the same `next_credential`; a retry after the new credential was used revokes the role; a retry after 60 s revokes the role; once only; only the previous step; the supersede guard still applies inside the grace.

What this costs, stated plainly: someone who stole credential P and presents it within 60 seconds of the owner's rotation, before the owner has used N, obtains N and so holds a live credential too. The owner's next resume then presents N, which the thief's resume did not consume (the grace does not rotate), so both hold N and neither is revoked until a normal rotation happens, after which whichever presents the older one is caught as reuse. Without the grace that thief would have revoked the role instead. The grace trades a small, time-boxed window for not breaking honest clients on every lost reply; 60 seconds and one use are the bounds. It also depends on the master secret being stable for those 60 seconds: rotating the SSM secret inside a grace window makes the re-derived value differ from the stored hash and the retry is treated as reuse (RUNBOOK.md section 6).

**Supersede guard (A3-07).** A resume that would take over a connection of the same role that was heard from within the last 25 seconds (the heartbeat window) is refused with the generic `unauthorized` and does **not** consume the credential, so a stolen credential cannot silently displace a live phone or TV. After 25 seconds of silence the old connection counts as dead and is superseded (`error superseded`, close 4409), and the TV is told through `peer.state` with the new generation on every phone (re)connect, which cancels an open window. The guard applies to both roles. Consequence for honest use: a TV that reconnects over a half-open socket can be refused for up to 25 seconds, and a client that stops permanently on `unauthorized` (ADR-0006 as amended by A6-02) must re-pair; a client that retries with back-off recovers after the window.

**Revocation (A3-11, SEC-A10).** Per-role epochs live on the room and each connection holds the epoch it authenticated at; it is compared on every message and not only at connect, so `unpair`, `room.close` and reuse take effect on the next message of any other connection of that role without waiting for a TTL. Expiry is enforced logically on every message; DynamoDB TTL deletion (which can lag by days) is only cleanup.

## 3. What the relay does not validate or protect

- **Meaning and truth of content.** Phrases, cue words, level values, device labels and `mic.state.mode` are checked for shape, range and size only. A client can send false microphone state or invented levels; the TV must treat observations as untrusted application data.
- **Device identity.** There is no device attestation. A credential is a bearer secret held in app memory (2 h, rotating); whoever holds the current one is that role. `Origin` is a browser protection against cross-site WebSocket hijacking, not identity: non-browser clients can set any `Origin`. `client.platform` is self-declared and never a trust signal; the production configuration only refuses the value `test`.
- **Confidentiality from the relay and the platform.** TLS protects client to relay only. The relay (and AWS API Gateway and Lambda in transit) handle plaintext payloads in memory. The product copy must keep the ADR-0002 wording ("validates without content logging or persistence"); the forbidden claims "end-to-end encrypted" and "relay never inspects payloads" are false for this design.
- **Message authenticity beyond the connection.** Messages are not individually signed. Integrity rests on TLS plus per-connection authentication; a compromised credential holder can send anything its role may send, in order.
- **Application state of the TV and phone.** The relay does not know TV stages, windows or attempts. It binds only room, role, generation, sequence and the active session id. Window and attempt identity are checked by the receivers (PROTOCOL.md section 4 step 10).
- **Delivery.** At-most-once forwarding with no queue. A peer that is offline gets `not_found` (level frames are dropped silently). In the Lambda adapter, concurrent invocations of one connection's messages can run out of order, so an individual `level` frame can be rejected as `replay` or forwarded late; the TV accounts frames by `frame_index` and coverage, and the window validity rules absorb gaps.

## 4. Abuse controls, and what they store

Controls (all in the core, so both adapters behave the same; thresholds are `DEFAULT_LIMITS` and `BACKOFF_*` in `src/core/relay-core.ts`):

| Control | Rule | Test |
|---|---|---|
| `$connect` budget | 20 per minute per source; over budget: HTTP 429 on AWS, handshake 429 locally | SEC-A03 |
| Unauthenticated connections | at most 5 concurrent per source; the slot is released on authenticate, disconnect or deadline | SEC-A03 |
| Failure delay | failures 1 to 3 free, then each attempt must wait 2 s, 4 s, 8 s, 16 s, 32 s, then 60 s; resets after 10 minutes without a failure; a delay, never a lock-out | SEC-A03 |
| Valid-code joins that end rejected, expired or abandoned | 6 per source per 10 minutes | SEC-A05 |
| `auth.resume` failures | 10 per minute per source and 10 per minute per `room_id` | SEC-A14 |
| `room.create` | 30 per source per hour | SEC-A03 |
| Live rooms | global cap 200 (`LiveRoomCap`, `ATR_LIVE_ROOM_CAP`); a room counts as live until it closes or has been idle 30 minutes | SEC-A03 |
| `pairing.refresh` | 1 per 10 s per room; the old code dies immediately; one live code per room | SEC-A05 |
| Burned codes | a TV reject, a wrong number pick (the TV sends `join.confirm` reject) and an unanswered join that expires each burn the code and push a fresh `pairing.code` to the TV | SEC-A05 |
| Global failed-join counter | the `join_failed` metric and its alarm only; it never blocks anyone (a global block would let an attacker lock everyone out) | SEC-A03 |

**What the counters store (A2-03, SEC-P07).** Counters are keyed by an HMAC of the source address (IPv4 /32, IPv6 /64) under a **key derived from the master secret and the UTC date**, so the key rotates daily and yesterday's counters can no longer be matched to today's sources; every counter item stores a count and an expiry of one hour at most and nothing else. No address appears in storage, logs, metrics, queue messages or error text (tests scan all of them). Consequences: the abuse state resets at 00:00 UTC (a patient attacker gets a fresh budget after midnight), and anyone holding both the master secret and the table could brute-force the 32-bit IPv4 space against the current day's keys, which is why the secret is a SecureString and not an environment value.

**Generic failures.** Every failed `auth.resume` (unknown room, wrong role, wrong or expired or revoked or reused credential, would-supersede, throttled, closed or idle room) answers the client with one error, `unauthorized`, with a constant detail. The specific reason (`credential_reused`, `would_supersede`, ...) is logged server-side as a closed-vocabulary code only. This removes the oracle that distinguished a live room from a dead one. Join failures are not generic: a failed `join.request` answers `not_found` for an unknown, burned or closed-room code and `expired` for a code past its 10 minute life, so a prober can learn that a code existed in the last minutes. That residual is accepted: the code space, the 10 minute life, the exponential delay and the per-source limits bound probing, and the information is worthless without the TV user's number match.

**Logging (A2-04, SEC-P02).** No line per message. Forwarded messages, dropped duplicates and peer-offline drops are counted and written as one `minute_aggregate` line per kind and message type per minute (counts only); only errors and security events (`origin_rejected`, `join_failed`, `credential_reuse`, `code_burned`, `superseded`, `unpaired`, `auth_deadline`, `kill_switch`, `internal_error`, ...) get their own line, with closed vocabularies for every field, 8-hex room prefixes and no addresses, ids, payloads, labels, phrases, cue text or credentials. The aggregate is written by the next invocation after the minute ends, so the last minute before a quiet period is written late and a recycled container loses it. EMF metrics (Lambda) carry the security counters only; the aggregated names are never emitted as metrics. Retention is 14 days at most on both log groups.

## 5. Close codes and error codes used

Close codes: 1003 binary frame; 1009 oversize; 4401 authentication deadline missed, credential expired or revoked, unknown connection; 4403 origin rejected; 4408 idle past the 25 s heartbeat window; 4409 superseded by a newer connection of the same role; 4410 unpaired or role revoked; 4411 room closed; 4429 too many unauthenticated messages, too many invalid messages, sustained rate abuse or a connect budget breach; 4503 kill switch. The relay never sends credentials, pairing codes or payload content in `error.detail`: details are constant strings.

**Client-visible behaviour on AWS (A3-09, differs from local only in the close code).** API Gateway's Management API cannot choose a close code: a `close` action is `DeleteConnection`, and the reason travels in the `error` message sent just before it. A refused `$connect` is HTTP 403 (origin), 429 (budget or concurrency cap) or 503 (kill switch); the local server refuses the upgrade with the same statuses. Authentication deadlines have no per-connection timer on Lambda, so the relay queues delayed SQS messages (5 s after `$connect`, 65 s after a join request, 5 s after a join ended) and a second Lambda calls `RelayCore.onDeadlineCheck`, which sends `error {unauthenticated, auth_deadline}` and then deletes the connection, exactly the message sequence the local sweep produces (`test/aws-adapter.test.ts` runs both and compares). An expired pending join is resolved first: the phone gets `join.rejected {expired}`, the TV gets `join.expired` and a fresh `pairing.code`, and the phone is dropped 5 s later. The check is idempotent and the deadline is also enforced on the connection's next message, so a lost, late or failed queue message only delays a close; if the queue is unavailable the relay fails open on the *timer* and still enforces the deadline logically. The consumer drops a queue message whose body is not exactly `{c, d, s}` with a domain and stage that match fixed patterns, so a forged message can never point the Management API client at another host.

## 6. Threats and where each is handled

| Threat | Mitigation | Residual risk |
|---|---|---|
| Cross-site WebSocket hijack | No cookies or ambient credentials; first-message authentication; exact `Origin` allowlist (no wildcards, no suffix or case matching); a present Origin that is not an exact match, including the literal `null` and an empty value, is refused at `$connect`; `origin_state` (`phone_origin`, `tv_preview_origin`, `absent`) is stored per connection; phone-role operations require `phone_origin`; the TV preview origin is a separate list, never in the production allowlist, and can never act as a phone | Non-browser forgery of `Origin` (not a goal) |
| Guessing a pairing code | 26.8-bit code under an HMAC, 10 minute life, one use, explicit TV confirmation by number matching; exponential per-source delay, 3 failures per connection, 6 ended valid joins per source per 10 minutes, burned codes, `join_failed` alarm | A distributed attacker with many sources can still try a few codes per source per window; success additionally needs the TV user to pick the right number for an unknown device label. There is no global block on purpose. |
| Guessing or stealing a credential | 256-bit random, hash at rest, constant-time compare, 2 h life, rotation on every resume, reuse revokes and tells the TV, epoch checked on every message, generic failure to the client | Bearer secret in memory; theft from a compromised device; the 60 s grace window (section 2) |
| Role takeover and races | Single-slot phone claim as one transaction (join, room and code together; no partial state; a busy phone receives only `join.rejected {busy}`); one pending join per room; single winner per resolution; generation and epoch bump on every claim; supersede guard | None known; concurrent-claim tests (1,000 iterations) on both stores |
| Replay and duplicates | Strict per-generation sequence by conditional write; duplicate ids dropped silently per (room, role); stale generations rejected | DynamoDB keeps recent ids for 60 s rather than the last 1024 |
| Pre-authentication resource use | 5 s deadline (SQS on AWS), 5 messages, 8 KB frames, no protected data before authentication, connect budget and concurrency cap per source, `room.create` 30 per hour per source, live-room cap, API Gateway throttle, a capped consumer | Public WebSocket endpoint: anyone can open connections within the throttle and the per-source budgets, and per-source budgets are weak against many addresses |
| Payload abuse (oversize, nesting, audio) | Size limit by bytes before parse, depth cap, audio guard, exact schemas, canonical forwarding | None known |
| Log leakage | Redacting logger with closed vocabularies; per-minute aggregates; the core emits only allowlisted events; Lambda adapters never log events or error objects; tests scan all log output for credentials, codes, phrases, cue text, labels, addresses, full ids | Platform logs outside our control (below) |
| Source address exposure | Addresses are hashed (HMAC under a daily-rotating derived key) before use and never stored or logged raw; counters expire within an hour; execution data tracing, API access logs, CloudFront and S3 logging and X-Ray are off in the template and asserted by tests | Platform records of API Gateway and CloudFront, which this template does not enable but AWS may keep for its own operation. **Never enable API Gateway execution logging with data tracing: it logs message bodies.** A leaked master secret plus the table allows brute-forcing the current day's IPv4 hashes. |
| Compression side channels | `permessage-deflate` is never negotiated on the local server (a test checks the handshake over plain and TLS); API Gateway offers none to the relay | Intermediaries outside the relay |
| Denial of service and cost | Stage throttle, reserved concurrency, consumer concurrency cap, kill switch, alarms, budget alert (COST.md section 4) | A budget alert is not a cap; sustained abuse inside the throttle still costs money |
| Stale or lost connections | Heartbeat window (local sweep), `$disconnect`, `GoneException` handling deletes the stale connection and notifies the peer, authentication deadlines | `$disconnect` is best effort and the Lambda deployment runs no scheduled sweep of authenticated connections, so a silently vanished peer is noticed only when a send hits `GoneException` or the client's own heartbeat times out |
| Phone page tampering or exfiltration | Private S3 bucket (public access blocked, bucket owner enforced, TLS-only policy), CloudFront OAC with always-sign, bucket policy scoped to the distribution ARN, CSP `default-src 'self'` with `connect-src` limited to self and the relay wss origin, `script-src 'self'`, no framing | CloudFront default certificate allows TLS 1.0 and above (a custom domain with ACM is needed for a 1.2 minimum); no WAF; anyone with deploy rights can change the page |
| Local development relay on a LAN | TLS required (refuses to start without it), certificates from a name-constrained local CA, loopback-only plain mode; HSTS only over TLS; `ATR_ENV=production` refuses insecure mode, preview origins, localhost and http origins and `platform: test` | The CA must be trusted on the phone; a leaked `ca.key` could mint certificates for local names only (name constraints), which are still dangerous on that LAN |
| The hashing secret | One SSM SecureString read at runtime, exact-ARN `ssm:GetParameter` for the two function roles, 10 minute cache, never an environment value, parameter, template literal or log field (tests assert it; the template has no `NoEcho` parameter at all); rotation procedure in RUNBOOK.md section 6 | The function roles can read it, and so can anyone who can assume them or who has `ssm:GetParameter` and decrypt rights; the managed-key decrypt permission is assumed, not proven (RUNBOOK.md section 6) |
| Test or development bypasses reaching production | `ATR_ENV=production` (set by the template when `Stage=prod`) rejects `client.platform: test`; a production configuration with preview origins or localhost origins fails to start; the template refuses `TvPreviewOrigins` on prod | Staging may enable them deliberately |

## 7. Properties for the reviewer to attack

1. A second connection can never use the room's single phone slot or reuse a consumed code, including under concurrency (`test/core.codes.test.ts` "the phone claim is one atomic step", the store conformance suite).
2. No path forwards a message before authentication or after revocation, expiry or supersede: try every state transition mid-stream, and every message in flight across a rotation.
3. Duplicate and replay handling at generation boundaries (resume while frames are in flight).
4. Origin matrix, especially phone-role operations with a missing Origin and TV-role operations with a foreign Origin, and the preview origin as a phone.
5. Log output for every message type and failure path (`services/relay/test/redaction.test.ts`, then try new sentinel content), and the minute aggregates.
6. DynamoDB expression correctness against the real service (the fake model is strict about placeholders and enforces conditions, but it is not DynamoDB; the `ConditionExpression` and `UpdateExpression` strings, the two `TransactWriteItems` calls and the `live-rooms` Query in `src/aws/dynamo-store.ts` should be run against DynamoDB Local or a staging table).
7. IAM scope in `infra/template.yaml` (both function roles) and `infra/iam/*.json` (drafts that have never been used), and the IaC assertions in `services/relay/test/infra.test.ts`, which are shown to fail on deliberately broken templates.
8. The grace window arithmetic in section 2: try presenting P, then N, then P again, at 59 s and 61 s, from two connections, with the secret rotated between.

## 8. Not yet exercised (pending external checks)

Real API Gateway behaviour (handshake status codes, `DeleteConnection` effect, `GoneException` timing, `$disconnect` delivery), the SQS-driven authentication deadlines on AWS (SEC-A02 needs staging: timings of the 5 s, 60 s and 65 s paths, the consumer's concurrency cap, the dead-letter path), real DynamoDB conditional and transactional semantics under load, SSM decryption by the function roles, CloudFront OAC and header behaviour, alarm and budget notification delivery, kill-switch rehearsal, physical-phone TLS trust with the local CA, and the Vega virtual device connecting to a locally generated certificate (not tested: do not promise self-signed WSS works on Vega).

Decisions and risks recorded for the lead (also in the handoff): the supersede guard applies to both roles and can refuse a legitimate TV reconnect for up to 25 s; the grace is stronger against lost replies but lets a thief who holds P within 60 s obtain N; the grace depends on the secret being stable for 60 s; the rate limit runs before the duplicate check (section 1); DynamoDB dedupe is time-bounded (60 s); abandoned rooms count toward the cap for 30 minutes; a failed deadline queue fails open on the timer; the daily source-key rotation resets abuse counters at 00:00 UTC; Lambda cannot choose close codes.
