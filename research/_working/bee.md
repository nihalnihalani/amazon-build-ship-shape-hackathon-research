# Bee (Wearable AI) track: developer data access, timing, and eligibility proof

Research date: 2026-10-03 (retrieved_at for every source below unless noted). Prefix: BEE.
Scope: what Bee data a hackathon developer can access, how (CLI / local HTTP API proxy / MCP / Agent Skill / direct API), timing semantics, auth and Developer Mode, device and Apple Watch requirements, product status and availability, and the minimum credible eligibility proof for the Bee track of "Build, Ship, Shape: Amazon Developer Hackathon".


## 0. Bottom line (for the planner)

1. **Access path is the user's own Bee account via the open-source `bee` CLI (npm `@beeai/cli`).** Everything else (local HTTP API proxy, MCP server, Agent Skill, realtime stream, webhooks) is a mode of that CLI or calls the same developer `/v1/*` API. Prereq: Bee app with Developer Mode unlocked (Settings > tap Version 5x). Docs say "Bee iOS app"; the hackathon FAQ says on Android Developer Mode only appears after pairing a Bee device; a Bee maintainer confirmed on GitHub (2026-08-17) that tapping the *app* version (bottom of Settings; on Android: user name > About) works on both platforms. [docs home/Getting Started, updated 2026-06-07](https://docs.bee.computer/docs); [Developer Mode, updated 2026-02-10](https://docs.bee.computer/docs/developer-mode); [hackathon FAQ](https://amazonappdev2026.devpost.com/details/faqs). Confidence: high.
2. **Data objects exposed:** profile (`me`), today brief (calendar events + emails; `--context` variant = daily summary, active todos, notes, conversations), conversations (with utterances/transcript, short summary, state, start/end time, location), daily summaries, facts (confirmed / pending), todos (+ Bee-suggested todos), journals / voice notes, insights, locations (clusters, recent visits, current), photos (imported from the phone gallery, not captured by the device), activity feed, change feed with cursor, keyword (BM25) and neural search. [CLI reference, updated 2026-06-07](https://docs.bee.computer/docs/cli). Confidence: high.
3. **Write access exists only for facts and todos** (create / update / confirm / complete / delete; accept or dismiss todo suggestions). Conversations, dailies, journals, insights, locations, photos are read-only in the reviewed CLI/MCP/API docs. Confidence: high for what is listed; "no write for conversations" is an absence in docs, not a documented restriction.
4. **Real-time exists, but it is processed-event streaming, not raw audio.** `bee stream` (and `GET /v1/stream` SSE through the proxy) emits `new-utterance` (text + speaker label + conversation_uuid), conversation lifecycle, todo and journal events, with at-most-once delivery; disconnected periods are lost and docs tell you to fall back to `bee sync`. `bee stream --webhook-endpoint ... --webhook-body <handlebars>` forwards events to a URL (client-side push from the CLI process; no server-side webhook registration was found). [Realtime Sync, updated 2026-06-07](https://docs.bee.computer/docs/realtime). Confidence: high. Raw audio: not available in any reviewed developer surface, and Bee/Amazon state audio is processed in real time and never stored ([Help Center Privacy & Security](https://bee-computer.notion.site/privacy-security); [About Amazon 2026-09-23](https://www.aboutamazon.com/news/devices/bee-private-compute-data-protection)).
5. **Polling / incremental:** `bee changed --cursor` (agentic sync, `meta.next_cursor`), `bee conversations transcript <id> --since <epochMs>`, `bee sync` incremental markdown export. [Agentic Sync](https://docs.bee.computer/docs/agentic-sync), [CLI](https://docs.bee.computer/docs/cli).
6. **MCP:** `bee mcp serve` (stdio) or `bee mcp serve-http --token <>=32 chars>` (local JSON-RPC over `POST /mcp` on 127.0.0.1:8790, bearer token). 34 tools listed; **no stream/subscribe tool** in the MCP catalog. The Bee docs do not state an MCP spec version or call the HTTP mode "Streamable HTTP" (that requirement applies to the Alexa+ track, not Bee). [MCP, updated 2026-06-07](https://docs.bee.computer/docs/mcp).
7. **Availability:** Bee Pioneer is $49.99 and ships **only to the US** (homepage + official Help Center); Android app is US-only (Android 13+); iOS app lists iPhone + Apple Watch (watchOS 10+) and is listed on the India App Store. No official India sale. New customers sign in with an Amazon account since 2026-09-23. The device stops recording after 15 minutes of silence by default.
8. **Eligibility hinge:** the rules require data "recorded and processed through an actual Bee device or an Apple Watch running the Bee software", demonstrated live in video and code. The FAQ's "CLI shouldn't require a Bee device, but it does require a bee account" is about *tool access*, not eligibility, and the separate Android FAQ says Developer Mode needs a paired device. Treat a real device (or Bee on Apple Watch) as mandatory for a submission.

## 1. Access surfaces (all built on one developer API)

| Surface | How to run | Auth | Notes | Source |
|---|---|---|---|---|
| CLI `bee` | `npm install -g @beeai/cli`; markdown default, `--json` for machine output | `bee login` (prints auth link, polls up to ~5 min for approval; `--qr`, `--no-wait`, `--token`, `--token-stdin`) | MIT, TypeScript, v0.7.3 latest release Jun 27 2026; last commit Aug 17 2026 | [CLI ref](https://docs.bee.computer/docs/cli) (updated 2026-06-07); [bee-cli repo](https://github.com/bee-computer/bee-cli) |
| Node library | `import { createBeeClient } from "@beeai/cli/lib"` | shells out to the `bee` binary, uses JSON flags | `bee.api.me()`, `bee.sse.streamJson({types:["new-utterance"]})` | [bee-cli README](https://github.com/bee-computer/bee-cli) |
| Local HTTP API | `bee proxy` (127.0.0.1:8787 or Unix socket `~/.bee/proxy.sock`) | proxy itself is **unauthenticated**, local-only; forwards any `/v1/*` | idle timeout 120 s default | [API](https://docs.bee.computer/docs/proxy) (updated 2026-06-07) |
| Direct API | `$BEE_API_BASE/v1/*` with `Authorization: Bearer $BEE_TOKEN` | bearer token | Bee API uses a **private CA**; client must trust Bee's cert (cert source in bee-cli `sources/certs.ts`). Base URL not published on the page | [API](https://docs.bee.computer/docs/proxy) |
| MCP server | `bee mcp serve` (stdio) / `bee mcp serve-http --token` (127.0.0.1:8790, `POST /mcp`, `GET /health`) / `bee mcp connect claude|claude-code|codex` | stored Bee login (stdio); bearer token >=32 chars (HTTP) | 34 tools; rejects non-localhost Host/Origin | [MCP](https://docs.bee.computer/docs/mcp) |
| Agent Skill | `npx skills add bee-computer/bee-skill` | needs Developer Mode; "can complete its own authentication flow automatically" | wraps the CLI; MIT; last commit Jun 7 2026; 0 releases/tags | [Skill](https://docs.bee.computer/docs/skill); [bee-skill repo](https://github.com/bee-computer/bee-skill) |
| Realtime | `bee stream` / `GET /v1/stream` (SSE) | same login | at-most-once; `--webhook-endpoint` + `--webhook-body` | [Realtime Sync](https://docs.bee.computer/docs/realtime) |

Practical implication: a hosted (cloud) app cannot call Bee without either (a) running the CLI/proxy alongside it with the user's login, (b) using the bearer token + private CA directly, or (c) pushing events out from a locally running `bee stream --webhook-endpoint`. The proxy and MCP HTTP server are explicitly localhost-only, so exposing them publicly contradicts the docs. The rules say no public-facing multi-user integration is required, so a single-user local bridge is acceptable.

## 2. Data model (fields observed in official docs/README examples)

Timestamps: the CLI markdown renders local time with relative age; sync files use ISO 8601 UTC; API `alarm_at` input is ISO 8601 but responses are epoch ms; search/transcript `--since/--until` are epoch ms. Sources: [CLI](https://docs.bee.computer/docs/cli), [API](https://docs.bee.computer/docs/proxy), [bee-cli README sync section](https://github.com/bee-computer/bee-cli).

| Object | Read | Write | Fields seen (examples) |
|---|---|---|---|
| Profile `me` | yes | no | timezone, first_name, last_name |
| Today brief `today` | yes | no | timezone, calendar_events, emails; `--context` = daily summary, active todos, notes, conversations |
| Conversation | list/get/related, transcript | delete events appear in stream (by user in app); no create/update in CLI | id (number), uuid, state (`processing`/`processed`/`COMPLETED`), title, short_summary, summary, start_time, end_time, created_at, updated_at, device_type (e.g. `ios`), primary location (address, lat/long, created_at), suggested links, transcriptions (`realtime: true/false`, speaker-labelled utterances) |
| Utterance | via conversation get/transcript, `bee now`, stream | no | text, speaker (`speaker_1` / named e.g. "Alex"), conversation_uuid; `--since <epochMs>` filters by spoken time |
| Daily summary | list/get/find by date | no | id, date_time, created_at, conversations_count, short summary, summary, email summary, calendar summary, locations, conversation list |
| Fact | list (confirmed / `--unconfirmed`), get, search | create, update, confirm, delete | id, text, confirmed, tags, created_at, timezone |
| Todo | list, get | create, update, complete, delete, `--alarm-at`, `--clear-alarm` | id, text, completed, alarm_at/alarmAt, created_at |
| Todo suggestion | list | accept, dismiss | "action items Bee proposed from your conversations" |
| Journal / voice note | list, get, search | no | id (string), state (`PREPARING` = recording, `ANALYZING` = processing, `READY`; stream example shows `processed`), text, aiResponse {message, cleanedUpText, followUp, todos[]} |
| Insight | list, get | no | fields not shown in docs |
| Location | clusters, recent visits (`--from/--to`), current | no | lat/long/name in stream payload |
| Photo | list (by daily id/date), get (download) | no | "imported from your phone's photo library, not captured by the device" |
| Activity / changes | `bee activity`, `bee changed --cursor` | no | `meta.next_cursor`, since, until, updated, timezone; facts, todos, dailies, conversations, journals arrays |

**Recorded vs processed vs fetched time.** Partly distinguishable: conversation `start_time`/`end_time` (when spoken) vs `created_at`/`updated_at` (record lifecycle) and daily `date_time` vs `created_at` (e.g. summary for 2024-01-15 created 2024-01-16T02:00Z in the README example); conversation `state` moves `processing` -> `processed`/`COMPLETED`; webhook template `{{timestamp}}` = when the CLI received the event. Utterance objects in the stream carry no timestamp field in the documented payload. Processing latency (how long after speech an utterance, summary, fact or todo appears) is **not documented**.

## 3. Timing: real-time vs polling vs snapshot

- **Realtime stream** (`bee stream`, `GET /v1/stream` SSE via proxy, `bee.sse.streamJson` in the Node lib). Event types: `connected`; `new-utterance`, `new-conversation`, `update-conversation`, `update-conversation-summary`, `delete-conversation`, `update-location`; `todo-created`, `todo-updated`, `todo-deleted`; `journal-created`, `journal-updated`, `journal-deleted`, `journal-text`. Docs: "real-time and does not guarantee delivery (at-most-once semantics)"; events during disconnection are lost; "If you need reliability/completeness, prefer a full `bee sync` snapshot." `--json` payloads have **no top-level `event` field**; filter with `--types`. [Realtime Sync, updated 2026-06-07](https://docs.bee.computer/docs/realtime). Confidence high.
- **What "real-time" means here:** `new-utterance` = "A new transcript snippet was captured" (text + speaker label). This is transcribed text after Bee's pipeline, not audio. No raw audio endpoint, audio download, or on-device hook was found in any reviewed doc, and Bee states audio is never stored. Sync files show a per-transcription flag `realtime: true|false`, implying Bee has both realtime and non-realtime (re)transcription passes; semantics not documented.
- **Webhook:** `--webhook-endpoint <url> --webhook-body '<handlebars>'` POSTs each filtered event from the running CLI process; template vars `{{message}}`, `{{event}}`, `{{timestamp}}` (ISO time the event was received), `{{raw}}`, `{{data.*}}`. This is the only "push to my server" mechanism found; it needs a long-running local `bee stream` process. Server-side webhook registration with Bee: not verified in reviewed sources.
- **Polling / changefeed:** `bee changed` (no cursor = bootstrap window; docs say "for example, last 10 hours", Skill says "roughly the last 24 hours"; the doc example spans 24 h) then `--cursor <meta.next_cursor>`; returns changed facts, todos, dailies, conversations, journals. Skill guidance: persist cursor only after processing for exactly-once handling. `bee conversations transcript <id> --since <epochMs>` for polling new lines of an in-progress conversation. [Agentic Sync](https://docs.bee.computer/docs/agentic-sync); [SKILL.md](https://github.com/bee-computer/bee-skill/blob/main/bee-cli/SKILL.md).
- **Field report on real-time fitness for voice commands (GitHub issue #4, opened 2026-05-21, open):** a Bee owner piping `bee stream --types new-utterance` to a VPS for wake-word actions reported the transcript stream was "too lossy for reliable action automation" (misheard commands, latency, at-most-once) and requested raw audio or low-latency transcript deltas with stable IDs. A Bee contributor (etown) replied 2026-06-07: use **journal text events** ("transcriptions from push to talk with the button") for this use case, and "we are considering adding a proper wake word support". Implication: for command-like or coaching interactions, design around the **button-press voice note -> `journal-text` / `journal-created` events** path, and treat ambient `new-utterance` as best-effort context. Single user report + one contributor reply: confidence medium. [issue #4](https://github.com/bee-computer/bee-cli/issues/4)
- **"Now" window:** `bee now` = conversations from the last 10 hours with utterances. [CLI](https://docs.bee.computer/docs/cli).
- **Snapshot:** `bee sync` -> `bee-sync/` markdown (facts.md, todos.md, daily/YYYY-MM-DD/summary.md, conversations/YYYY-MM-DD/<id>.md), incremental via `.bee-sync.json`; deletions are **not** reconciled. [bee-cli README](https://github.com/bee-computer/bee-cli).
- **Not documented:** end-to-end latency from speech to `new-utterance`, to conversation `processed`, to daily summary / facts / todo suggestions; whether the stream works when the phone app is backgrounded; whether the Apple Watch source emits the same events.

## 4. Auth, Developer Mode, device prerequisites

- Developer Mode "is required for Bee CLI and Bee Skill to connect to your Bee account". Enable: update the Bee iOS app, open Settings, tap **Version** 5 times; verify with `bee login` + `bee status`. [Developer Mode, updated 2026-02-10](https://docs.bee.computer/docs/developer-mode). Getting Started repeats "must have the **Bee iOS app** installed and Developer Mode unlocked". [Getting Started, updated 2026-06-07](https://docs.bee.computer/docs).
- Android: the Help Center says the Bee app runs on Android 13+ in the United States; Google Play lists "Bee AI" (5K+ downloads, updated 2026-09-03); the bee-cli README links it, while the bee-skill README still says "Android Coming Soon" (stale). The developer docs only describe the iOS Developer Mode path. Hackathon FAQ: "You need to pair a Bee device before Developer Mode becomes available in the Bee app's Settings" (Android question). [FAQ](https://amazonappdev2026.devpost.com/details/faqs).
- **Developer Mode practical tip (GitHub issue #13, 2026-07-27..08-17):** a Bee collaborator (ex3ndr, also the latest bee-cli committer) wrote that a common mistake is tapping the *device firmware* version; instead open the app Settings screen, scroll to the bottom, and tap the *app* version 5x, which "Works on both platforms". The reporter confirmed Android: tap top-right user name > About > tap App Version 5x. The reporter had received Bee hardware first; whether Developer Mode appears with no paired device was not tested in the thread. The collaborator also said "we didnt monitor this issues", so GitHub issues are not a reliable support channel. [issue #13](https://github.com/bee-computer/bee-cli/issues/13). Confidence: medium (one maintainer comment + one user confirmation).
- Login flow: `bee login` prints a link of the form `https://bee.computer/connect#{requestId}`; user approves; request expires in ~5 minutes; `--no-wait` for agents; alternative `--token`/`--token-stdin`; `--proxy` to delegate auth to another local process. Not OAuth client registration; there is no published app/client-ID flow for third-party multi-user apps (not verified in reviewed sources). [CLI](https://docs.bee.computer/docs/cli); [SKILL.md](https://github.com/bee-computer/bee-skill/blob/main/bee-cli/SKILL.md).
- Direct API: bearer token + Bee private CA. [API](https://docs.bee.computer/docs/proxy).
- Encryption claims (vendor): "All Bee data is end-to-end encrypted and accessible only to you" (bee-skill README); docs home lists "End-to-end encrypted". Vendor statement, not independently verified.
- **Rate limits / quotas:** none documented. Only per-command `--limit` maxima appear in SKILL.md (e.g., activity 20, related 10, photos 20, location clusters 20, insights 50, todo suggestions 50, recent visits 100; search 1-100). Not verified: API rate limits, token lifetime, refresh.

## 5. MCP and Agent Skill specifics

**MCP** ([docs, updated 2026-06-07](https://docs.bee.computer/docs/mcp)):
- Transports: stdio JSON-RPC 2.0 (`bee mcp serve`, uses stored login) and local HTTP JSON-RPC over `POST /mcp` (`bee mcp serve-http`, default 127.0.0.1:8790, `GET /health`, bearer token >=32 chars via `--token` or `BEE_MCP_HTTP_TOKEN`, token never printed, rejects non-localhost Host/Origin).
- The docs do **not** name an MCP spec revision or say "Streamable HTTP", nor document SSE/GET support on `/mcp`, sessions, or resumability. Treat it as a local POST JSON-RPC endpoint (not verified as spec-compliant Streamable HTTP). This matters only if a team wants one server to double as an Alexa+ MCP server: build your own 2025-11-25 Streamable HTTP server and call Bee from inside it.
- 34 tools: `bee_status`, `bee_search`, `bee_search_facts`, `bee_list_facts`, `bee_get_fact`, `bee_create_fact`, `bee_update_fact`, `bee_delete_fact`, `bee_get_recent_activity`, `bee_get_today`, `bee_list_conversations`, `bee_get_conversation`, `bee_get_conversation_transcript`, `bee_get_related_conversations`, `bee_get_daily_summary`, `bee_list_daily_summaries`, `bee_list_voice_notes`, `bee_search_voice_notes`, `bee_get_voice_note`, `bee_list_todos`, `bee_create_todo`, `bee_update_todo`, `bee_complete_todo`, `bee_delete_todo`, `bee_get_todo_suggestions`, `bee_accept_todo_suggestion`, `bee_dismiss_todo_suggestion`, `bee_get_insights`, `bee_get_insight`, `bee_get_location_clusters`, `bee_get_recent_visits`, `bee_get_current_location`, `bee_get_photos`, `bee_get_photo`.
- Gaps vs CLI: no MCP tool for `bee now`, `bee changed`, `bee stream`, `bee sync` in the listed catalog (transcript `since` param partly substitutes). So an MCP-only agent must poll; for live behaviour use `bee stream` alongside.
- `bee_search` params: `query`, `limit`, `filter` (all|conversations|daily|facts), `sortBy` (relevance|mostRecent), `mode` (keyword|semantic), `since`, `until` (epoch ms).

**Agent Skill** ([docs](https://docs.bee.computer/docs/skill); [repo](https://github.com/bee-computer/bee-skill); [SKILL.md](https://github.com/bee-computer/bee-skill/blob/main/bee-cli/SKILL.md)):
- Install `npx skills add bee-computer/bee-skill`; a single `bee-cli/SKILL.md` (name `bee-cli`) plus a packaged `bee-cli.skill`; MIT; 14 commits, last Jun 7 2026; no tags/releases.
- Content: capability map (question -> command), "ALWAYS start with `bee now`", source-of-truth rule (summaries are AI-generated and may be inaccurate; utterances are "verbatim and authoritative"), pagination via `next_cursor`, `bee login --no-wait` flow, changefeed cursor discipline, sync, a "Deep Learning About the Owner" multi-subagent batch workflow that builds `user.md` from full history, MCP and stream/proxy command lists, and strong privacy guidance ("Treat all Bee information as highly confidential").
- Requirements: Bee CLI installed; Bee account with authenticated session.

## 6. Bee native features (do not rebuild these as your "innovation")

From [bee.computer homepage, undated, retrieved 2026-10-03](https://www.bee.computer/) and docs: summaries and takeaways per conversation, suggested to-dos, patterns and insights, daily memories / daily summaries, search and chat ("Search for and talk about anything"), conversation templates, integrations and actions, voice notes (journals), facts (confirmed/pending), location history, today brief built from calendar and email, photos imported from the phone gallery. Talk to Bee via the Bee Pioneer device, iOS or Android apps, or an Apple Watch. Implication: a project that only summarizes conversations, extracts to-dos, or answers "what did I talk about" duplicates first-party features; the rules' own "Obvious" list (notification relay, basic logging) points the same way.

- **Price / purchase:** Bee Pioneer Edition **$49.99**; "New orders ship in 1-2 business days"; "**Bee currently ships only to the United States.**"; "**Bee Pioneer currently supports iOS only**"; up to 7 days (160 h) battery; dual mics; button start/stop with green LED while capturing; ~40 languages; wristband + clip. ## 9. Hackathon eligibility: what the rules require vs what the FAQ says

Rules ([Official Rules](https://amazonappdev2026.devpost.com/rules), submission period 2026-08-31 to 2026-10-23 12:00 PT):
- Track definition: "connects to data recorded and processed through a Bee device or Apple Watch running Bee software, using Bee's CLI, MCP, or Agent Skills. The demo must show the project using that data to deliver value to a user." Priority use cases: education, developer experience, personal productivity.
- Overview page paraphrase: "your video and code need to show your project actually using live Bee data to do something for a user, mentioning Bee isn't enough" ([overview](https://amazonappdev2026.devpost.com/), saved `.firecrawl/hackathon-overview.md`).
- Repo requirement: "The project must be connected to data recorded and processed through an actual Bee device or an Apple Watch running the Bee software. The demo video and code must show the project actually using that Bee data to do something for a customer, mentioning Bee without demonstrating a live data interaction does not count. No public-facing integration ... is required."
- Runtime hook: for Alexa+, Bee, Ring "the repository must demonstrate use of your track's required technology at runtime in your code — imported and actually called (a library import, an app/backend entry point, or a loaded agent/flow/MCP config), not just named in the README."
- Judging "Creative" examples for Bee: cross-device orchestration (Bee + Echo + Fire TV), ambient context informing a productivity workflow, education via Agent Skills for on-wrist coaching, "advance use of the facts and insights capabilities", real-time functionality, self-improvement workflows, synced insights for meetings across teams. "Obvious": simple notification relay, basic data logging.

FAQ ([FAQs page](https://amazonappdev2026.devpost.com/details/faqs)):
- "Bee: The CLI shouldn't require a Bee device, but it does require a bee account."
- "You need to pair a Bee device before Developer Mode becomes available in the Bee app's Settings." (Android question)

**Discrepancy:** the FAQ implies the CLI may work with only an account, but (a) Developer Mode is a documented prerequisite for the CLI and Skill, (b) on Android the FAQ itself says Developer Mode needs a paired device, and (c) the rules (which govern) require data recorded and processed through an actual Bee device or Apple Watch. An account with no device-recorded data cannot satisfy the rules, and simulated/fixture data would fail the "live data interaction" test. Recommend asking organizers in the Devpost discussion whether a Watch-only account is acceptable if no Pioneer device can be obtained (do not rely on the FAQ line).

**Minimum credible eligibility proof (recommended video beats, <3 min total):**
1. Show the physical Bee Pioneer on the wrist with the green capture LED on (or Bee running on an Apple Watch), and a short real conversation/voice note being captured (re-arm capture first: default auto-stop after 15 minutes of silence).
2. Show it arriving in the Bee app (conversation/voice note list) to establish Bee processing.
3. Show the project pulling that same item via the CLI/MCP/Skill: e.g., terminal `bee stream --types new-utterance --agent` or `bee changed --json`, or the agent's MCP tool call (`bee_get_conversation_transcript`) with a visible conversation id/timestamp that matches the app.
4. Show the project doing something useful with it (the value step), ideally writing back through a supported write (create/confirm a fact, create/complete a todo) and showing the result in the Bee app.
5. In the repo: the `@beeai/cli/lib` import / `bee` subprocess call / MCP config actually loaded at runtime; a README run section; redacted sample outputs (never commit real transcripts or tokens).
Inference (not an organizer statement): steps 1-3 are what distinguishes "live Bee data" from mocked data; keep mocked fixtures only for tests and label them.

## 10. Design implications for project ideas (inference from the evidence above)

- **Best-supported "real-time" pattern:** `bee stream --types new-utterance,update-conversation,todo-created --json` (or the Node lib's `bee.sse.streamJson`) feeding a local agent, with `bee changed --cursor` as the reliability backstop and `bee conversations transcript <id> --since` for catch-up. Show both in the demo to answer judges' "real time functionality" criterion while acknowledging at-most-once delivery.
- **Command / coaching interactions:** use the Pioneer button push-to-talk voice note path (`journal-text`, `journal-created` with `aiResponse.todos`) rather than parsing ambient utterances for commands (issue #4 evidence). Fits the rules' "on-wrist coaching" and "real time functionality" examples.
- **Cross-device orchestration (Bee + Echo/Alexa+ + Fire TV):** run the Bee CLI on a laptop/server you control; forward selected events with `--webhook-endpoint` to your own backend (AWS Lambda/API Gateway) that then drives an Alexa+-style MCP server or a Fire TV app. Keep the Bee proxy/MCP HTTP on localhost per docs.
- **Write-back is limited to facts and todos.** Ideas that "fix" transcripts, rename speakers, or edit summaries inside Bee are not supported by the developer tools reviewed; keep such corrections in the project's own store and, where useful, confirm/create facts or todos.
- **Use the facts/insights/todo-suggestion surfaces** (explicitly named in the judging "Creative" list): e.g., confirm/reject pending facts with evidence from utterances, accept/dismiss todo suggestions, contradiction detection (Skill example prompt).
- **Trust model:** follow the Skill's rule (utterances authoritative, summaries may be wrong) and show provenance links (conversation id + utterance) in the UI; reviewers (TechCrunch, App Store reviews) report speaker misattribution and spurious "memories".
- **Privacy/consent:** Bee data is highly sensitive; demo with consenting participants and redact. The TechCrunch reviewer got confirmation before recording a call; Engadget notes recording-consent laws vary by jurisdiction.
- **Logistics risk for an India-based team:** the device ships only to the US (homepage + Help Center); the Android app is US-only (Help Center); the iOS app is listed on the India App Store (iPhone + Apple Watch) but service availability outside the US is not verified; an iPhone (+ optional Apple Watch, watchOS 10+) is the safest phone path. Hindi is a supported language. Allow time for shipping and for building up real data (inference: multi-day insights and daily summaries need several days of wear).

## 11. Gaps / unverified / contradictions

Contradictions found:
1. **FAQ vs rules on device need.** FAQ: CLI "shouldn't require a Bee device, but it does require a bee account". Rules: data must be "recorded and processed through an actual Bee device or an Apple Watch running the Bee software". Rules govern; FAQ addresses tool access only.
2. **Android Developer Mode.** Docs describe only the iOS app path ("Bee iOS app", App Store). FAQ says Android needs a paired Bee device before Developer Mode shows. Homepage says "Bee Pioneer currently supports iOS only" while also saying you can talk to Bee through "iOS or Android mobile apps". bee-skill README still says "Android Coming Soon"; Google Play lists "Bee AI" (5K+ downloads, updated 2026-09-03). Help Center (undated) says the Android app runs on Android 13+ in the United States with the same core features. Net: Android app exists (US); Developer Mode on Android works via user name > About > tap App Version 5x (GitHub issue #13, maintainer + user confirmation, 2026-08-17) and needs a paired device per the hackathon FAQ; the developer docs only document iOS. iPhone remains the lowest-risk path.
3. **Photos provenance.** CLI docs: photos are "imported from your phone's photo library, not captured by the device". SKILL.md capability table: "Photos captured by the device". Trust the CLI docs (more specific, same date).
4. **`bee changed` default window.** Agentic Sync doc: "for example, last 10 hours"; SKILL.md: "roughly the last 24 hours"; doc example spans 24 h. Always pass a cursor after bootstrap.
5. **Sign-in change.** Developer docs (Feb/Jun 2026) predate the 2026-09-23 move to Amazon-account sign-in for new customers; `bee login` approval flow for Amazon-account users is not documented.
6. **Battery life.** bee-cli README: "14-day battery life"; homepage and Help Center: up to 7 days / 160 hours (an open GitHub issue #15 asks the same). Low impact.
7. **Homepage freshness.** bee.computer is undated and shows a stale Black Friday widget; price/shipping lines may lag reality.
