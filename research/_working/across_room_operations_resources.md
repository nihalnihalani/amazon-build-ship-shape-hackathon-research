## What these resources change in the build plan

1. **Reproducible infrastructure.** Version the chosen SAM templates, environment parameters and deployment instructions. Inspect the CLI install/prerequisite pages and Hello World tutorial linked from the fetched SAM guide before relying on exact commands. Pin a supported Lambda runtime and SDK. Validate/build/plan in a permitted environment; deployment success and cleanup need their own evidence.
2. **Correct callback authorization.** Give the relay execution role narrowly scoped callback permissions, derive the actual endpoint from deployed configuration, and use SDK signing. Never copy the guide's illustrative us-east-1 endpoint for a Mumbai deployment. Treat established-but-stale connections, early callback, GoneException and missing disconnect events as explicit recovery cases. Do not copy the sample's generic console.log(error) into a privacy-sensitive relay without redaction.
3. **Private origin, public phone page.** Put static phone assets in a private ordinary S3 origin with OAC, read-only distribution-scoped access and public access blocked; expose the page over CloudFront HTTPS. OAC protects origin access; it does not authenticate app visitors or replace room authorization. Verify direct anonymous S3 access fails and the CloudFront page still loads with microphone-capable HTTPS.
4. **Spending controls with honest limits.** For this Lambda/API Gateway/DynamoDB workload, EC2/RDS stop actions do not stop relay traffic. IAM/SCP actions can constrain selected operations but are not an instantaneous hard account-wide spending cap. Design app/provider request limits, Lambda concurrency, bounded retention, abuse protection and an explicit controlled relay-disable runbook. Any automation capable of denying access needs a tested rollback and owner-approved scope; alerts should not silently take away judge access.
5. **Alarms need delivery tests.** Define non-content service/error/latency metrics and meaningful evaluation periods/missing-data policy. Wire an appropriate alarm notification target and test actual delivery separately. A successful alarm definition or temporary SetAlarmState test demonstrates only the configured part exercised; it does not alone prove metric ingestion, threshold evaluation, confirmed notification subscriptions or recipient receipt.

Items 1–5 are implementation recommendations/inferences from the fetched documentation, not claims of a deployed architecture or proven operational limits. Cloud billing freshness and exact account/region-specific budget-action behavior need separate current documentation/account verification before promising an automatic spending cut-off.
